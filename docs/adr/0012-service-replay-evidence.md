# ADR 0012: Service-mode replay evidence preservation and promotion semantics

## Status
Accepted (v0.3.0-in-progress, Phase C2.2)

## Context
Phase C2.1 (ADR-0011) gave Service mode real candidate recovery, but every candidate it produces is, by construction, `inferred` -- a static-feature similarity score, never a causal claim. Closing that gap requires a real counterfactual-replay path: intervene on a candidate's presence/absence in a derivation's reconstructed context, compare behavior, and classify the result. Phase C2.2 builds that path without reimplementing the replay science Lite mode already has (`skillrewind.replay.*`), and without weakening any of the evidence-class boundaries ADR-0011 established.

Two design questions had to be answered up front:
1. Does a replay-confirmed candidate *become* recorded, or does it stay a distinct evidence class alongside the original inferred score?
2. When replay cannot even run (no derivation to reconstruct, a runner crash, insufficient repetitions, low fidelity) -- is that a rejection, or something else?

## Decision

### 1. Replay-confirmed is a new `edges` row, never a rewrite of the `CandidateScore` row
Mirroring `DerivationRepository`'s materialization pattern (ADR-0011 decision 2), `ReplayRepository.finalize_run` only ever *creates or updates a dedicated `edges` row* (`source=ancestor`, `target=descendant`, `relation="hidden-influence"`) carrying the replay-derived evidence class (`replay-confirmed`, `rejected`, or `unresolved`). It never touches the originating `CandidateScore` row's `raw_score`, `feature_breakdown_json`, or `evidence_class` -- those stay exactly as Phase C2.1 recorded them, permanently `inferred`. A `latest_replay_run_id`/`latest_replay_verdict`/`latest_replay_at` pointer is the only thing added to `CandidateScore`, and it is documented as a denormalized summary for the candidate-history view, not a second copy of the evidence. This directly satisfies the milestone's invariant 5 ("preserve the original inferred score breakdown ... do not overwrite or lose prior evidence when replay evidence is added") and invariant 1 ("an inferred score alone must never become recorded or replay-confirmed") -- there is no code path where scoring alone can produce a `replay-confirmed` or `recorded` row; only `ReplayRepository.finalize_run`, called only after a real replay attempt, can.

A second replay attempt against the same (ancestor, descendant) pair updates the existing `edges` row's evidence class rather than inserting a duplicate (the table already has a `(source, target, relation)` uniqueness constraint from Phase A), but preserves the superseded run's ID in `payload_json["prior_replay_run_ids"]` rather than silently discarding it -- a later verdict is authoritative for serving/traversal purposes, but the fact that an earlier attempt happened and what it concluded remains inspectable.

### 2. Every "replay could not confirm influence" outcome is `unresolved`, never `rejected`
`REJECTED` means the paired present/withheld comparison found *no behavioral difference* under a fidelity-passing, sufficiently-repeated, successfully-run replay -- a real negative result. Everything else that stops replay from reaching that comparison is `UNRESOLVED_*`:
- `UNRESOLVED_RUNNER_FAILURE` -- the runner itself errored (mirrors Lite mode's existing verdict).
- `UNRESOLVED_FIDELITY` -- fidelity components didn't meet `config.replay_fidelity.minimum_confirmed` (existing verdict).
- `UNRESOLVED_REPETITIONS` -- fewer than `MIN_REPETITIONS_FOR_SIGNIFICANCE` (5) repetitions were run, so the paired-bootstrap estimate isn't reported as significant (existing verdict).
- `UNRESOLVED_MISSING_INPUTS` (new in this phase) -- the candidate's descendant has no recorded derivation to reconstruct at all, so no runner could ever be invoked.

`skillrewind.replay.service_mode.VERDICT_TO_EVIDENCE_CLASS` is the single mapping table from verdict to evidence class, and every `UNRESOLVED_*` member maps to `EvidenceClass.UNRESOLVED`, none to `EvidenceClass.REJECTED`. This is exhaustive and typed (a `dict[ReplayVerdict, str]`), so adding a future verdict without updating the mapping is a `KeyError` at the call site, not a silent misclassification.

### 3. Missing reconstruction inputs are accepted at submission, not rejected
A candidate whose descendant has no recorded derivation is still a legitimate replay-run *submission* -- `POST /api/v1/replay/runs` returns 202 and creates a `ReplayRun` row with `target_derivation_id = NULL`; the `lineage.replay` job handler recognizes this and finalizes the run as `UNRESOLVED_MISSING_INPUTS` without ever invoking a runner. This is deliberately different from the *separate* CAS-integrity check (missing/corrupted content for the candidate's own artifacts), which *is* rejected synchronously with a 422 at submission time, because that is a request-validation problem detectable without attempting replay at all, whereas "no derivation recorded" is a data-availability condition specific to this candidate that the milestone's invariant 2 requires be resolved through the same classification pipeline as every other unresolved outcome (auditable, visible in the run's evidence, consistent with runner-failure/fidelity-failure/insufficient-repetitions).

### 4. Tenant isolation is actor-scoped, not a new multi-tenant schema
This codebase has no formal tenant-partitioning concept anywhere else (every artifact/derivation/candidate is visible to any authenticated `read`-scoped key). Building one for replay runs alone would be new, out-of-place scope. Instead, `ReplayRun.created_by_actor` (the submitting API key's `actor`) is treated as a lightweight tenant boundary for this one resource: `GET /api/v1/replay/runs/{id}[...]` requires the requesting key's actor to match the run's creator, or to carry `admin` scope. This satisfies the milestone's cross-tenant-isolation requirement for the one resource this phase introduces without pretending to retrofit multi-tenancy onto artifacts/derivations/candidates, which remain shared-workspace resources as they always have been.

### 5. Checkpoint-resumability is per-repetition, driven by persisted payload, not just a resume flag
`skillrewind.replay.service_mode.run_service_replay` takes `already_done: dict[repetition_index, payload]`. On resume, a repetition already in that map is *not* re-executed -- its `RunnerOutput` is reconstructed from the exact payload persisted for it (`present_outputs`/`withheld_outputs`/`present_vector`/`withheld_vector`/`fidelity_components`), so the final classification after an interrupted-and-resumed run is byte-identical to what an uninterrupted run would have produced. This is what makes "crash after each major checkpoint and successful resume" safe even when the crash happens after the *last* repetition (i.e. resuming a run where every repetition is already persisted correctly recomputes the same fidelity/comparison/classification from stored data rather than asserting on missing in-memory state).

## Consequences
- Reading a candidate's full evidentiary history requires two queries, exactly as it did after ADR-0011: `GET /api/v1/lineage/candidates/{id}` (or `/explanation`) for the original inferred score, and `GET /api/v1/lineage/candidates/{id}/history` for the same score plus every replay run submitted against it. Neither ever collapses into the other.
- The `edges` row a confirmed replay produces is picked up by `LineageRepository.graph` (explicit evidence-class filter) exactly like Phase C2.1's inferred/recorded edges, but never by `LineageRepository.descendants`/`.ancestors` (hard-wired to `recorded` only, per ADR-0011 decision 4) -- replay-confirmed evidence, however strong, does not silently become "recorded" lineage. Promoting it to `recorded` would require a separate, explicit revocation/quarantine action (not built in this phase), consistent with invariant 4 ("serving resolution must remain unaffected by inferred or replay results unless a separate revocation/quarantine transition is executed").
- `skillrewind.replay.service_mode.run_service_replay` has no direct database dependency (repetition persistence and checkpointing are injected callables) specifically so it stays unit-testable and so the exact same function serves both the real job handler and the crash-simulation test in `test_service_replay_job_handler.py` without a second, parallel implementation.
- A future replay-triggered revocation/quarantine workflow (out of scope here) can safely consume `edges` rows with `evidence_class="replay-confirmed"` as its trigger signal, since this phase guarantees no other code path can produce that evidence class.
