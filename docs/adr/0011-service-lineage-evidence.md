# ADR 0011: Service-mode lineage/evidence architecture — recorded vs. inferred stays a hard boundary

## Status
Accepted (v0.3.0-in-progress, Phase C2.1)

## Context
Phase C2 gave Service mode a real artifact repository and CAS-backed ingest/retrieval, but no way to record *how* an artifact was derived, no way to query lineage over that schema, and no way to run hidden-lineage candidate recovery outside a Lite-mode `Workspace`. Building this raised one architectural question the rest of the milestone hinges on: how do "recorded" (explicitly asserted by a caller) and "inferred" (computed by a similarity scorer) facts stay distinguishable end to end — in storage, in traversal, and in the API — rather than quietly merging into one generic "lineage edge" concept.

This is not a new problem for this codebase. Lite mode already hit it once: `skillrewind.lineage.closure.build_graph` was written specifically because an earlier, generic closure implementation traversed edges of *any* evidence class, which meant a merely-inferred hidden-lineage candidate could silently expand what a revocation barrier treated as "recorded" fact. `CHANGELOG.md`'s v0.2.0 "Fixed" section documents that bug. Phase C2.1 had to avoid reintroducing it in Service mode's parallel schema.

## Decision
1. **One edge table, two disjoint write paths, evidence class always explicit.** Service mode's existing `edges` table (already had an `evidence_class` column from Phase A) is used for both recorded derivation-input edges and inferred candidate-recovery edges. `DerivationRepository` only ever writes rows with `evidence_class = "recorded"`; `CandidateRepository`/`lineage.service_recovery` only ever write `candidate_scores` rows with `evidence_class = "inferred"` (a separate table, not `edges` — a candidate score is not yet a lineage edge at all; see point 3). Neither writer can accidentally produce the other's evidence class because they are different code paths writing to different tables with a hardcoded value, not a shared writer branching on a caller-supplied flag.
2. **`derivation_inputs` and `edges` are two views of the same recorded facts, kept in lockstep by one repository method, not two independent sources of truth.** A caller records a derivation's parent inputs via `POST /derivations/{id}/inputs`; `DerivationRepository.add_inputs`/`set_output` materializes each into the corresponding `edges` row (`evidence_class="recorded"`) as soon as the derivation's output artifact is known. There is no code path that writes to `derivation_inputs` without also (eventually) writing the matching `edges` row, and no code path that writes a `recorded` `edges` row except through this materialization.
3. **A candidate score is not an edge.** `CandidateScore` rows are deliberately a separate table from `edges`, not an edge with `evidence_class="inferred"` inserted into the same table `LineageRepository` traverses. This is a stronger boundary than Lite mode's (which does insert inferred `InfluenceEdge` rows into the same table, relying entirely on evidence-class filtering at query time). The Service-mode candidate-recovery path was built after the Lite-mode bug above was already known, so it removes the failure mode at the schema level instead of only at the query level: even a `LineageRepository` query that forgot an evidence-class filter could not accidentally traverse a candidate score, because a candidate score is not in the traversed table.
4. **Recorded-closure query methods take no caller-supplied evidence-class override.** `LineageRepository.descendants`/`.ancestors` (the "recorded closure" query family) hard-code `evidence_classes=("recorded",)` internally and expose no parameter to widen it. A caller who wants to see inferred/other-evidence-class edges must use `LineageRepository.graph`, a visibly different method with a different name and an explicit `evidence_classes` parameter, whose response labels every edge's evidence class rather than collapsing them into one generic "dependency." `tests/integration/test_derivation_lineage_api.py::TestRecordedClosureInvariant` regression-tests exactly this: an inferred edge inserted directly into `edges` must not appear in `GET .../descendants` or `.../ancestors`, but must appear (labeled `inferred`) in `GET .../graph`.
5. **A candidate score can only ever be promoted to `replay-confirmed` by a real replay result.** No code in `skillrewind.lineage.service_recovery` or the candidate API can set `evidence_class` to anything but `inferred` for a freshly-scored candidate, and `calibrated_probability` is always persisted as `None` — this milestone does not implement a calibration pipeline (see `docs/completion-matrix-v0.3.md`'s Phase F row), so a raw scorer output must never be presented as a probability. Promoting a candidate to `replay-confirmed` requires a Service-mode replay API, which is explicitly **not** built in this milestone — see the "next backend gate" note in `STATUS.md`. This ADR's decision is only that the schema and repository boundary is ready for that future write path, not that it exists yet.

## Consequences
- Reading Service-mode lineage state always requires picking the right query: "what do we know for certain" (`descendants`/`ancestors`, recorded-only, non-configurable) versus "what does the evidence graph look like including inference" (`graph`, explicit evidence-class filter, evidence labeled per edge). This is a deliberate two-method API rather than one method with a mode flag, so a caller cannot get the recorded-only guarantee wrong by passing the wrong flag value — the method name itself is the guarantee.
- `CandidateScore` living outside `edges` means a future replay-confirmation write path will need to *create* a new `edges` row (not update the `CandidateScore` row's evidence class) when a candidate is confirmed by replay, mirroring exactly how `DerivationRepository` materializes recorded edges. This is intentional: it keeps "a candidate score exists" and "a lineage edge is recorded" as separately auditable facts, and it means `GET /artifacts/{id}/resolve` (serving resolution) can safely never query `candidate_scores` at all — it only ever needs `artifacts.status`/`edges`/`waivers`/`quarantine`, so an inferred candidate score categorically cannot influence a serving decision through this endpoint by construction, not merely by convention. This is tested in the acceptance scenario (`tests/integration/test_lineage_recovery_acceptance.py`, step 14).
- The feature-extraction bridge (`skillrewind.features.bridge`) and the candidate-recovery service (`skillrewind.lineage.service_recovery`) both call the same feature-similarity functions Lite mode's `skillrewind.lineage.candidates` calls (`expression_similarity`, `implementation_similarity`, `operational_similarity`, `behavioral_similarity`, `graph_similarity`, `temporal_proximity`, `score_candidate`) rather than reimplementing scoring for Service mode. Only the data-access plumbing (Service-mode repositories + CAS instead of a Lite-mode `Workspace`) differs. A change to feature-similarity behavior only ever needs to happen in one place.
