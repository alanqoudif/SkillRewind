## 1. Project identity

> **SkillRewind: Recovering Hidden Influence Lineage for Verified Revocation in Self-Evolving LLM Agents**

Author and copyright identity to preserve:

- **Faisal Ali Said Al-Anqoudi**
- **Nuqta Technologies**
- License: **Apache-2.0**

Core product statement:

> AI agents can learn reusable skills. SkillRewind makes persistent learned artifacts attributable, revocable, selectively rebuildable, and verifiable within a declared evidence boundary.

Core research problem:

> When a skill, memory, trace, prompt patch, generated code artifact, or other persistent agent artifact is revoked, deleting the source is insufficient if its influence has propagated into descendants whose provenance edges are missing, transformed, or incomplete. SkillRewind must recover plausible hidden influence, test selected relationships through counterfactual re-derivation, quarantine confirmed or high-risk descendants, rebuild them from clean support, verify safety and retained utility, and emit a bounded attestation that clearly distinguishes facts, inferences, interventions, and unresolved uncertainty.

This is a serious open-source AI systems and security project. It must look and behave like infrastructure that researchers and agent-platform engineers can actually install, inspect, test, and extend.

## 3. Non-negotiable scientific and engineering rules

### 3.1 Never fabricate research results

Do not invent benchmark numbers, model comparisons, citations, statistical significance, screenshots, user counts, performance claims, or security guarantees.

Any number presented as a result must be generated by a command in this repository and map to:

- a frozen configuration;
- a seed;
- a code version or commit when available;
- raw machine-readable outputs;
- an analysis script; and
- an explicit environment manifest.

Use labels such as `target`, `expected`, `smoke-run`, `illustrative`, or `measured` accurately.

### 3.2 Do not call correlation causal

Maintain these evidence classes and semantics:

1. **recorded** — directly captured as an input or exposure;
2. **inferred** — supported by static or observational evidence;
3. **replay-confirmed** — supported by a paired intervention within a declared replay boundary;
4. **rejected** — tested but not supported under the declared intervention and probes;
5. **unresolved** — not replayable, inconclusive, outside budget, or outside coverage.

A recorded edge proves exposure, not behavioral causation. A similarity score is never replay confirmation. A rejected edge is not universal proof of no influence. A replay-confirmed edge must always include replay fidelity and probe limitations.

### 3.3 Never claim perfect unlearning

SkillRewind does not promise erasure from foundation-model parameters or all future behavior. Permissible claims must be bounded, for example:

> No active artifact remains in the recorded and replay-confirmed closure, and the target canary behavior was not observed under the declared verifier suite.

Never write:

> The model perfectly forgot the information in every possible context.

### 3.4 No fake implementations

Do not create buttons, commands, endpoints, or status labels that pretend a capability exists when the backend is a stub. A capability may be marked `experimental`, but it must execute real logic and have tests. Otherwise omit it or clearly expose it as `not implemented` outside the primary workflow.

Do not leave `TODO`, `pass`, dummy return values, placeholder metrics, fake queues, or hard-coded success states in the production path.

### 3.5 Safety of benchmark payloads

All security effects must be inert and sandbox-only. Allowed canaries include:

- emitting a unique token;
- selecting a mocked Boolean flag;
- writing a marker inside a temporary sandbox directory;
- calling a local fake endpoint;
- selecting a disallowed branch in a simulator.

Never use real credentials, real exfiltration, destructive commands, production endpoints, malware, persistence, or uncontrolled network actions.

### 3.6 Determinism and reproducibility

All synthetic generation, graph mutation, replay fixtures, and evaluation must accept explicit seeds. Record dependency locks, schema versions, container/environment digests where available, model identifiers, configuration hashes, and replay limitations.

### 3.7 Security defaults

Fail closed for unresolved high-severity artifacts in strict or balanced revocation modes. Disable network access in replay sandboxes by default. Never log secrets. Never execute arbitrary host shell commands from an API request.

## 9. Canonical serialization, hashing, CAS, and tamper evidence

### 9.1 Canonicalization

Create one deterministic canonical JSON function used for manifests, evidence, audit events, and attestations. Define and test:

- UTF-8 encoding;
- sorted object keys;
- stable separators;
- normalized datetimes in UTC;
- no NaN or Infinity;
- stable enum serialization;
- clear treatment of binary data through digests rather than embedded bytes.

Document whether the implementation follows an existing canonical JSON standard or a project-specific profile. Never imply standard compliance unless actually implemented.

### 9.2 Digests

Use SHA-256 as the mandatory interoperable digest. Optional algorithms may be added only as secondary values.

Artifact IDs should follow a stable pattern such as:

```text
skill://deploy-fastapi@sha256:<full-hex-digest>
trace://run-184@sha256:<full-hex-digest>
```

Validate schemes and full digest length. Existing short example digests may remain accepted only in legacy/demo compatibility mode, not as production IDs.

### 9.3 Content-addressed storage

Implement a storage protocol and at least:

- local filesystem CAS;
- optional S3-compatible CAS.

Local writes must be atomic. Stream uploads while hashing. Deduplicate identical content. Prevent path traversal and symlink escape. Enforce configurable object-size limits. Verify digest on read when configured.

Support:

- put;
- get/open stream;
- exists;
- metadata;
- integrity check;
- export;
- conservative garbage-collection planning.

Do not automatically delete evidence objects. GC should default to dry-run and respect retention, references, revocation history, and legal holds.

### 9.4 Hash-chained audit log

Add an append-only audit event table or log where each event includes the previous event hash and its own canonical hash. Provide:

```bash
skillrewind audit verify
skillrewind audit export
```

The verifier must detect deletion, reordering, or modification within the available chain. Clearly state that this is tamper-evident, not protection against an attacker who can replace the entire trusted root.

## 13. Hidden-lineage candidate recovery

Implement a real, explainable static candidate system. It does not need to solve all research questions, but it must be nontrivial, tested, and useful.

### 13.1 Candidate neighborhood

Avoid all-pairs comparison by building a bounded neighborhood using configurable signals:

- derivation time window;
- shared task or task family;
- shared candidate context pool;
- shared model or builder recipe;
- graph proximity;
- shared tools or output type;
- artifact kind compatibility;
- logical version adjacency.

The system must expose why a candidate entered the neighborhood.

### 13.2 Feature families

Implement at least the following feature families.

#### Expression trace

- normalized Unicode text;
- lowercase/case-folded tokens where language-appropriate;
- token n-gram similarity;
- character n-gram similarity;
- normalized phrase fingerprints;
- optional local embedding adapter behind an extra;
- explicit language metadata;
- no network model download in default tests.

#### Implementation trace

For Python and structured code/config where possible:

- AST normalization that removes irrelevant identifiers while preserving operations;
- imports and fully qualified API call signatures;
- literal and configuration fingerprints with secret redaction;
- control-flow approximations;
- normalized JSON/YAML trees;
- generic token fallback for unsupported languages.

Do not execute code to extract static features.

#### Operational trace

- ordered tool-call sequence;
- tool-call multiset;
- argument-shape signatures with values redacted or normalized;
- trigger/step/output graph;
- sequence edit distance or n-gram overlap;
- file and artifact production types.

#### Behavioral trace

- deterministic probe vector;
- canary activation vector;
- mocked policy-choice vector;
- utility-test vector;
- exact source of each behavioral feature.

Behavioral features must come from safe stored probe outputs, not from executing arbitrary untrusted artifacts on the host.

#### Graph and temporal trace

- shared recorded ancestors;
- shared descendants;
- path proximity;
- version adjacency;
- temporal distance;
- common context pool;
- bridge/cut relevance.

### 13.3 Strict negatives

RewindBench and candidate scoring must include independently developed same-function artifacts. Add negative indicators for:

- common boilerplate;
- common library templates;
- same words with different behavior;
- shared tools with different triggers;
- temporal proximity without derivation support;
- equivalent safe implementations created from independent roots.

### 13.4 Explainable scorer

Create a deterministic weighted scorer with configuration such as:

```yaml
features:
  expression: 0.20
  implementation: 0.25
  operational: 0.20
  behavioral: 0.20
  graph: 0.10
  temporal: 0.05
thresholds:
  candidate: 0.35
  high_confidence: 0.80
```

The exact defaults must be justified by smoke calibration or clearly labeled as provisional. Return a score breakdown, missing features, candidate-neighborhood reasons, and scorer version.

Add an optional offline calibration pipeline using the RewindBench train split, for example logistic regression plus Platt or isotonic calibration. Never train on the test split. Save model metadata, feature schema, split hash, and calibration report. The deterministic hand-weighted scorer must remain available without a trained model.

Measure calibration with Brier score and expected calibration error where sufficient labels exist.

## 14. Counterfactual re-derivation and replay

This is the defining component. Implement it carefully.

### 14.1 Replay abstraction

Define a `DerivationRunner` protocol that can reconstruct a target derivation from a frozen specification.

At minimum implement:

1. **DeterministicFixtureRunner** — fully offline runner for demos, CI, and RewindBench;
2. **SandboxedSubprocessRunner** — executes allowlisted benchmark recipes inside an isolated container or constrained subprocess;
3. **OpenAICompatibleRunner** — optional adapter using environment configuration, never required for tests.

The runner must never be selected solely by user-controlled arbitrary module paths from the API. Use a registry of approved runners.

### 14.2 Paired intervention

For candidate ancestor `A` and target derivation `D`, execute matched conditions:

- `present`: reconstruct `D` with `A` available exactly as in the retained candidate context when possible;
- `withheld`: reconstruct `D` with `A` removed;
- optional `clean-control`: replace `A` with a safe same-function control;
- optional `irrelevant-control`: include an unrelated artifact to detect generic perturbation.

Keep all other reconstructable variables fixed:

- task snapshot;
- workspace snapshot;
- recipe;
- tools;
- model identifier;
- decoding configuration;
- environment;
- seed where supported.

Record every unavoidable difference.

### 14.3 Replay fidelity

Compute a fidelity report from components such as:

- task snapshot match;
- workspace match;
- recipe match;
- model match;
- decoding-config match;
- environment match;
- tool-schema match;
- candidate-context reconstruction;
- seed support;
- elapsed drift.

Do not collapse fidelity to a magic number without exposing components. A low-fidelity replay must become unresolved or have downgraded evidence according to policy.

### 14.4 Output comparison

Implement composable comparators:

- exact bytes/text;
- canonical JSON;
- normalized AST/code signature;
- tool-call sequence and graph;
- produced artifact set;
- canary activation;
- policy-choice vector;
- deterministic verification suite;
- task utility score;
- optional semantic comparison as supporting evidence only.

A user must be able to inspect the specific observed effect.

### 14.5 Statistical handling

For deterministic fixture runs, record a deterministic result.

For stochastic runs:

- support configurable repetitions and matched seeds where possible;
- use paired analysis;
- report effect size and uncertainty;
- use an appropriate paired binary test or paired bootstrap for canary activation;
- use paired bootstrap confidence intervals for continuous utility differences;
- avoid claiming significance with inadequate sample size;
- record every failed or excluded repetition and its reason.

### 14.6 Classification

A candidate may be `replay-confirmed` only when:

- the intervention is valid;
- replay fidelity meets policy minimum;
- target behavior changes or a declared effect threshold is crossed;
- utility/control checks rule out a broad meaningless perturbation as far as the suite can test;
- evidence and reports are persisted.

Classify as:

- confirmed;
- rejected within boundary;
- unresolved due to fidelity;
- unresolved due to insufficient repetitions;
- unresolved due to budget;
- unresolved due to runner failure.

Do not turn runner errors into rejected edges.

## 15. Active replay selection

Implement a budget-aware selector rather than exhaustive replay in production mode.

Candidate priority should incorporate:

- inferred edge probability;
- severity of the revoked behavior;
- expected increase in affected closure if confirmed;
- bridge/cut importance;
- uncertainty or expected information gain;
- replay cost estimate;
- replay fidelity estimate;
- artifact serving status.

A reasonable initial explainable priority form is:

```text
priority =
    severity_weight
  * closure_impact
  * bridge_weight
  * uncertainty_value
  * fidelity_estimate
  / max(expected_cost, epsilon)
```

Do not hard-code this without configuration and documentation. Recompute priorities after each confirmed or rejected edge because graph impact changes.

Budgets must support at least:

- maximum replay calls;
- maximum input/output tokens when available;
- maximum wall-clock duration;
- optional monetary ceiling.

Provide baselines:

- exhaustive replay;
- highest inferred score first;
- random seeded selection;
- active impact-aware selection.

Persist the selection trace so a paper can reproduce why each replay was chosen.

## 16. Revocation semantics and barrier-first behavior

Implement three policies:

### 16.1 Forensic

- no serving-state changes;
- calculate recorded blast radius;
- infer candidates;
- optionally replay under a specified budget;
- emit a report and attestation.

### 16.2 Balanced

- immediately make revoked roots and recorded descendants non-servable;
- infer hidden candidates;
- replay decision-relevant candidates;
- quarantine replay-confirmed descendants;
- optionally quarantine high-severity/high-confidence unresolved candidates according to config;
- rebuild eligible artifacts;
- verify and republish clean successors;
- retain unresolved risk in the final attestation.

### 16.3 Strict

- immediately make revoked roots and recorded descendants non-servable;
- quarantine high-confidence inferred descendants before replay;
- fail closed for unresolved high-severity candidates;
- require verification before any successor is active.

### 16.4 Transactionality and idempotency

- applying the barrier must be transactional;
- API and CLI write operations accept an idempotency key;
- rerunning the same revocation must not duplicate state or artifacts;
- state transitions are validated;
- crashes and worker restarts resume safely;
- aliases and serving lookup must never return revoked or quarantined versions;
- an audit event is emitted for every state transition and manual action.

### 16.5 Dry run

Support a dry-run plan that does not mutate serving state and clearly labels estimates:

```bash
skillrewind revoke plan --root <id> --policy balanced --budget replay_calls=20
```

The real command must require an explicit reason and severity:

```bash
skillrewind revoke start \
  --root <id> \
  --policy balanced \
  --reason "Unsafe benchmark canary rule" \
  --severity high \
  --budget replay_calls=20
```

## 18. Clean-room rebuild

Implement a rebuild planner and at least one working rebuild runner for deterministic benchmark cases.

A rebuild plan must:

1. begin from an affected artifact;
2. inspect its derivation recipe and support set;
3. exclude revoked roots;
4. exclude recorded descendants that are not valid support;
5. exclude replay-confirmed contaminated ancestors;
6. apply policy to high-risk unresolved artifacts;
7. retain clean inputs and explicit controls;
8. validate that the recipe and environment themselves are not revoked;
9. produce a plan digest before execution.

A rebuild must:

- create a new immutable artifact;
- never modify the old one;
- link `rebuilt-from`, `replaces`, and clean support edges;
- preserve logical identity only through alias update after verification;
- record the exact clean support set;
- run in the sandbox;
- retain logs and costs;
- remain quarantined if verification fails.

For optional LLM rebuilds, use the same provider abstraction and record model drift. Never silently use a different model.

## 38. Decision rules when trade-offs arise

1. **Truth over appearance.** A smaller real feature beats a polished fake one.
2. **End-to-end over disconnected breadth.** Preserve the working revocation vertical slice.
3. **Recorded facts over inferred certainty.** Keep evidence classes strict.
4. **Offline reproducibility over provider dependence.** The default demo and tests remain local.
5. **Fail closed for high-severity uncertainty.** Especially after barrier application.
6. **Immutable evidence over convenient mutation.** Create successors rather than editing history.
7. **Simple documented infrastructure over unnecessary distributed complexity.** SQLite/local CAS first, PostgreSQL/workers second.
8. **Backward compatibility over silent breakage.** Version schemas and commands.
9. **Security defaults over convenience.** Network-off sandbox and scoped auth.
10. **Measured results over marketing.** No benchmark claims before real runs.
